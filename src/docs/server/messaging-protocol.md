# Messaging protocol

The drachtio server is controlled by drachtio-srf applications using a utf8-based messaging protocol over a tcp (or, optionally, TLS) connection.

Because some developers have expressed an interest in integrating other language frameworks (e.g. go) to the drachtio server, this section documents the core message protocol.

As per the documentation found elsewhere on this site, drachtio supports both inbound and [outbound](../srf/advanced-topics.md#outbound-connections) connections.  To begin with, we will focus here on describing the message flows for inbound connections; the differences for outbound connections are described [at the end of this page](#outbound-connections).

## Basic message format
Messages are utf8-encoded.

Each message starts with a decimal number indicating the number of bytes in the message (again, this is utf-8 so number of characters does not necessarily mean number of bytes!), followed by a hash sign ('#').  The number of bytes specified does **not** include these leading decimal digits or the hash sign -- they indicate the length of the payload that follows.  The length specifier may be at most 5 digits long; if a client sends a length specifier containing anything other than digits, or more than 5 digits, the server considers the stream to be corrupt and closes the connection.

The message payload that follows this consists of 1 or more lines of data, where lines are separated by a CRLF.

The first line of payload data consists of a list of tokens, where each token is delimited by a '|' character.  The first token is always a unique message identifier (drachtio-srf and the server both use a v4 uuid), and the second token is the message type.  Empty tokens are significant (i.e. `a||b` is three tokens, the second of which is empty) and many messages end the first line with a trailing '|'.  When SIP messages are exchanged between application and server, these are carried starting on the second line of data, and are simply represented exactly as they appear "on the wire" between SIP endpoints.

### How to see messages being exchanged
For those interested, note that it is possible to generate a trace of all messaging between the client and the server by passing a `logger` function in the options to `srf.connect` (or `srf.listen`), e.g.:
```js
const Srf = require('drachtio-srf');
const srf = new Srf();
const fs = require('fs');
const log = fs.createWriteStream('/tmp/messages.log', {flags: 'a'});

// this will cause messages between client and server to be logged to a file
srf.connect({
  host: '127.0.0.1',
  port: 9022,
  secret: 'cymru',
  logger: (msg) => log.write(msg)
});
```

::: info Note
drachtio-srf always passes messages sent to the server to the logger, but for performance reasons messages received from the server are only passed to the logger when debug output for the `drachtio:agent` namespace is enabled (e.g. `DEBUG=drachtio:agent`).  Alternatively, when the drachtio server is running with a log level of `debug` it logs every message it reads from and sends to each client.
:::

## Connection and authentication
An inbound connection scenario starts when an application, acting as a TCP client, connects to a drachtio server on its configured admin port (by default, port 9022).  The server can additionally be configured to accept TLS-encrypted connections on a separate port (the `tls-port` attribute of the [admin](configuring.md#admin-section) element); the message protocol is exactly the same over a TLS connection.  See [Using TLS to encrypt messages between application and server](../srf/advanced-topics.md#using-tls-to-encrypt-messages-between-application-and-server) for details.

After the connection is established, the application must authenticate itself via the shared secret that is configured in the `drachtio.conf.xml` configuration file (or via the `--secret` command line option) on the server.  If the client is authenticated, the server returns information including the sip hostports (e.g. list of address:port) that the server is listening on.

Let's look at an example of a successful authentication.  Not all of this will immediately be clear, but we will review the individual message elements below.
```
===>56#12ad33a1-9f33-40b7-b327-b2e32bfcd9e8|authenticate|cymru|

<===177#2f8216a3-babf-4cdb-93c6-254fe8dba42d|response|12ad33a1-9f33-40b7-b327-b2e32bfcd9e8|OK|udp/203.0.113.10:5060,tcp/203.0.113.10:5060|v0.9.11|udp/10.0.0.121:5060,tcp/10.0.0.121:5060
```
> Note: the direction `===>` indicates a message sent from an application to the server; the reverse indicates a message sent from the server to the application

We see that after connecting, the application sends an authenticate request to the server.  The authenticate request consists of a single line containing the following tokens:

* a unique message identifier, generated by the client application (needs to be unique only for this client),
* the message type ('authenticate')
* the shared secret ('cymru')
* optionally, a comma-separated list of tags that identify this application (empty in the example above).  Tags are used by the server when routing incoming requests to a specific group of applications, as described [below](#outbound-connections).

```
# authenticating with tags
===>80#12ad33a1-9f33-40b7-b327-b2e32bfcd9e8|authenticate|cymru|sbc-inbound,sbc-outbound
```

The server validates the shared secret, and returns a message consisting of one line, containing the following tokens:

* a unique message identifier for the response
* the message type ('response')
* the message id of the associated request
* the response status ('OK')
* a comma-delimited string containing the sip hostports the server is listening on, in the form `transport/address:port`.  If an external address has been configured for a SIP contact, the external address is reported here.
* the version of the drachtio server (e.g. 'v0.9.11')
* a comma-delimited string containing the local sip hostports the server is listening on (i.e., always the local address, even if an external address has been configured)

If the shared secret is incorrect, the server responds with a status of 'NO' and a reason, and then closes the connection:
```
<===102#2f8216a3-babf-4cdb-93c6-254fe8dba42d|response|12ad33a1-9f33-40b7-b327-b2e32bfcd9e8|NO|incorrect secret
```

At this point, the client has connected and authenticated successfully, but it has not yet registered the SIP request types that it would like to receive.  That happens next.

## Registering to handle SIP requests
In order to notify the server that the application wishes to handle specific SIP request types, it is necessary to issue a 'route' command.  This is typically the next thing a client application does after authenticating.  It is only necessary to register for request types once, during startup (i.e., after actually handling an incoming request it is not necessary to re-register in order to get further requests).
> Registering for request types is taken care of automatically in a drachtio-srf app when a `srf.invite()` statement is processed, for example.

```
# registering to receive INVITEs
===>49#5e60fef0-409f-4980-a859-94810d002ebb|route|invite
<===85#e7470b05-95be-448e-94cd-3935292c4956|response|5e60fef0-409f-4980-a859-94810d002ebb|OK
```
> Note: to register for multiple request types (e.g. INVITE and REGISTER) the application must issue separate 'route' commands.

The 'route' command consists of a single line containing the following tokens:

* a message id
* the command ('route')
* the SIP request type, in lower case (e.g. 'invite').  A request type registered in upper case will never match.

The response, as before, contains its own message id as well as the message id of the request, and the status ('OK').

The same command is used to subscribe to [call detail records](#call-detail-records), by specifying 'cdr:attempt', 'cdr:start', or 'cdr:stop' in place of a SIP request type.

When more than one connected application has registered for the same request type, the server distributes new incoming requests among them in round-robin fashion.  Requests within an existing dialog (e.g. a re-INVITE or BYE) are always sent to the application that is managing that dialog.  If no connected application has registered for an incoming request type (and no [request handler](configuring.md#request-handlers-section) has been configured), the server rejects the request with a 503 Service Unavailable.

At this point, the server will start sending SIP requests of the requested type to the application for handling.  Let's look at what happens next.

## Handling an incoming SIP request
Let's start with something simple: receiving a SIP INVITE and sending a non-success response.

The basic message flow is this:

* The server receives a SIP INVITE, selects the client application to send it to for handling, and sends a 'sip' message type to the client app containing the full SIP request message, as well as additional detail (e.g. the source address and port etc)
* The client application receives the message and sends a sip response message, containing at least the SIP status as well as any headers that it wants set to any non-default values.
* The server sends out the SIP response on the network and then sends another message back to the client containing the exact message that was sent out over the wire.

With that as background, let's examine the message trace.  To make it interesting, we will have the client application add a custom SIP header to the response.

We will also see now our first example of messages containing multiple lines, since we are now carrying SIP messages back and forth between client and server:

Let's examine the first message -- the one sent by the server to the application, giving it an incoming INVITE message to handle.

As usual, after the length specifier we see the message payload begins with the message identifier.

After that, we have the message type, which in this case is 'sip'.  We've now seen almost all of the message types (there aren't that many!), so let's pause here and briefly give the full list.

Message types sent by the application to the server:

* 'authenticate'
* 'route'
* 'remove_route'
* 'sip'
* 'proxy'
* 'ping'

Message types sent by the server to the application:

* 'response'
* 'sip'
* 'cdr:attempt'
* 'cdr:start'
* 'cdr:stop'

If the server receives a message with any other message type it responds with a status of 'NO' and the reason 'Unknown message type', and then closes the connection.

### Message types explained

**authenticate** - Sent by the client to authenticate with the server using a shared secret, as described [above](#connection-and-authentication).

**route** - Sent by the client to register interest in receiving a specific SIP method type (e.g., INVITE, REGISTER), or call detail records. The client will receive incoming SIP requests of that type.

**remove_route** - Sent by the client to unregister interest in receiving a specific SIP method type.  The tokens are the same as for the 'route' command.
```
===>56#7f1c0a52-3b7e-4d0e-9a51-0c6a0b3c5f11|remove_route|invite
<===85#c3b0e2d4-6a1f-4f5e-8c2b-7d9e0f1a2b3c|response|7f1c0a52-3b7e-4d0e-9a51-0c6a0b3c5f11|OK
```

::: info Note
'remove_route' removes *all* of the request types (and CDR subscriptions) that the client has registered for, not just the one named in the command.  To keep receiving other request types, re-issue 'route' commands for them.
:::

**sip** - Carries a SIP message between client and server. Sent by the server to deliver SIP requests and responses received from the network (and, occasionally, requests that the server itself generated on behalf of the application -- see [below](#requests-generated-by-the-server)).  Sent by the client to send SIP responses, new SIP requests, requests within a dialog, and CANCELs.

**response** - Sent by the server to acknowledge a command from the client.  The third token is always the message id of the client message that it relates to, and the fourth token is the status: 'OK' for success, or 'NO' / 'NOK' for failure, in which case the fifth token contains a reason.  Note that a single client 'sip' or 'proxy' command may result in more than one 'response' message (see [Proxying a request](#proxying-a-request)).

**proxy** - Used to proxy an incoming SIP request to one or more destinations. See [Proxying a request](#proxying-a-request) below.

**ping** - An application-level keepalive on the connection.  The server responds with a status of 'OK' and the text 'pong'.  This is supported by drachtio server versions v0.8.2 and later, and drachtio-srf sends pings periodically when the `enablePing` option is supplied to `srf.connect` or `srf.listen` (with an optional `pingInterval` in milliseconds, which defaults to 15000 and must be between 5000 and 300000).
```
===>41#4b8e1c6a-2d3f-4e5a-9b7c-8d6e5f4a3b2c|ping
<===90#9a7b6c5d-4e3f-4a2b-8c1d-0e9f8a7b6c5d|response|4b8e1c6a-2d3f-4e5a-9b7c-8d6e5f4a3b2c|OK|pong
```

> Note: independently of application-level pings, the server also enables TCP keepalives on each client connection, using the interval (in seconds) configured by the `tcp-keepalive` attribute of the [admin](configuring.md#admin-section) element (default 45; 0 disables).

**cdr:attempt**, **cdr:start**, **cdr:stop** - [Call Detail Record](#call-detail-records) events sent by the server to the application.

### Incoming sip messages

In the case of a 'sip' message sent by the drachtio server we have the following tokens on the first line of the message payload:

* message id
* message type ('sip')
* message source ('network' or 'application', depending on whether the server received the message from the network or sent it on behalf of the application)
* length of the SIP message, as received over the wire
* transport protocol ('udp', 'tcp', or 'tls')
* source address
* source port
* time message was received, in the form HH:MM:SS.uuuuuu (UTC)
* unique id assigned by the server for this SIP transaction
* unique id assigned by the server for this SIP Dialog (empty when there is no dialog yet, as is the case for a new incoming request)

For a new incoming request (i.e., one that is not within an existing dialog), two further tokens are included:

* the local address of the SIP transport the request was received on
* the local port of the SIP transport the request was received on

In the example above these are '127.0.0.1' and '5060'.  drachtio-srf makes this available to applications as `req.receivedOn`.

Following the first line of payload the SIP message in its entirety is provided.

### Responding to a request

At this point it is the responsibility of the application to return the desired SIP response that it wishes the server to send out.  We see in the example above that the application also uses the 'sip' message type to accomplish this.  The first line of payload contains the following tokens:

* message id
* message type ('sip')
* the transaction id that the sip response pertains to
* the dialog id (empty, in the case of a response)

Following that we have the message itself.  Note that it is **not** necessary to provide the full SIP response message -- based on the transaction id, most of the headers will be supplied by the drachtio server.  The application must minimally provide the SIP status line (in our example, drachtio-srf is populating several other headers such as To, From, etc but this should not be necessary).  Additionally, if a body is desired in the response (which is not in our example), then that would be provided by the application as well (in the normal way of separating the body from any headers with two (2) CRLFs).  The server recognizes the message as a response because the start line begins with 'SIP/'.

The drachtio server sends out the indicated response and then notifies the application of the exact SIP response that was sent out over the wire.  This allows the application to learn about information, such as the tag on the SIP To header, that the server itself would have applied.

This final message has the following payload:

* message id
* message type ('response')
* related message id (in this case, the 'sip' response message sent by the application)
* message status ('OK')
* message source ('application', indicating this was a message sent by the application)
* length of the SIP message
* transport protocol used
* remote address sent to
* remote port sent to
* time message was sent, in the form HH:MM:SS.uuuuuu (UTC)
* related transaction id
* the dialog id that the server uses to represent this SIP Dialog.  The dialog id is formed from the Call-ID and the tag of the From header, e.g. `<call-id>;from-tag=<tag>`.

> Note: the additional tokens at the end of the first line (a blank token, and the string 'Msg sent:') can be ignored; they are placeholders.

If the server is unable to send the response (for example, because the transaction id is unknown, or the transport the request arrived on has since been closed) it returns a status of 'NOK' and a reason, e.g. `<msgid>|response|<request msgid>|NOK|transport for response has been shutdown or closed`.

## Sending a SIP request
To send a new SIP request (e.g., when acting as a UAC) the application sends a 'sip' message with the following tokens on the first line of payload:

* message id
* message type ('sip')
* transaction id (empty for a new request)
* dialog id (empty for a request outside of a dialog)
* optionally, a SIP URI of an outbound proxy to send the request through (drachtio-srf populates this from the `proxy` option to `srf.request` and `srf.createUAC`)

Following that is the SIP request, consisting minimally of a request line (e.g. `INVITE sip:1234@10.0.0.1 SIP/2.0`) and any headers and body the application wishes to supply.  As with responses, the server fills in the headers the application does not provide (Via, Call-ID, CSeq, From/To tags, Contact, etc).

```
===><len>#<msgid>|sip||\r\n
INVITE sip:1234@10.0.0.1 SIP/2.0\r\n
Content-Type: application/sdp\r\n
...
```

The server generates a unique transaction id for the request, sends it out, and responds with a 'response' message containing the request exactly as it was sent over the wire.  The first line of that 'response' contains the same tokens as described in the previous section (message source 'application', length, transport, address, port, time) followed by the transaction id that the server assigned to the request, and the placeholder 'Msg sent:'.  The application uses that transaction id to correlate SIP responses that subsequently arrive from the network, which are delivered as 'sip' messages (with message source 'network') carrying that same transaction id (and, once a dialog has been established, the dialog id).

A few variations are worth noting:

* **Requests within a dialog** (e.g. re-INVITE, INFO, BYE, or the ACK for a 200 OK to an INVITE) are sent by providing the dialog id in the fourth token.  The server fills in the Call-ID, CSeq, From and To headers etc. based on the dialog state.  If no dialog id is provided but the request includes a Call-ID header that matches an existing dialog, the server treats the request as being within that dialog.  If the dialog no longer exists, the server returns a 'NOK' status.
* **CANCEL** is sent by providing the transaction id of the INVITE being canceled in the third token (and leaving the dialog id empty).
* **ACKs for non-success final responses** are generated automatically by the server; the application should not send them.

### Requests generated by the server
In certain situations the server itself will send a request within a dialog managed by an application, for example a BYE sent because an ACK was never received for a 200 OK.  When this happens the server notifies the application with a 'sip' message having a message source of 'application' and a transaction id of 'unsolicited', so that the application can clean up its state for the dialog.

## Proxying a request
Rather than responding to an incoming request, an application can ask the server to proxy it.  The 'proxy' command has the following tokens on the first line:

* message id
* message type ('proxy')
* the transaction id of the incoming request to proxy
* 'remainInDialog' if the server should insert a Record-Route header and remain in the signaling path; otherwise empty
* 'fullResponse' if the application wishes to receive the final response from the network; otherwise empty
* 'followRedirects' if the server should follow 3XX responses; otherwise empty
* 'simultaneous' to fork the request to all destinations in parallel, or 'serial' to try them one at a time
* the provisional timeout (e.g. '2s' or '1500ms'): how long to wait for a 100 Trying before trying the next destination
* the final timeout (e.g. '60s'): how long to wait for a final response before canceling the current attempt and trying the next destination
* one or more destination SIP URIs, each in its own token

Following the first line, the application may include a SIP request (the request line is ignored) whose headers will be added to the proxied request.

```
===><len>#829ba63e-5010-4719-b72f-cb3cf6f4aab2|proxy|8f62909b-0f25-4bb8-b0fc-2c0ec88a4afe|remainInDialog||followRedirects|serial|2s|60s|sip:a@destination1.example.com|sip:b@destination2.example.com\r\n
INVITE sip:a@destination1.example.com SIP/2.0\r\n
X-Custom: some value\r\n
```

If 'fullResponse' was not requested, the server responds with `OK|done` as soon as the request has been sent out to at least one destination.  If 'fullResponse' was requested, the server sends a 'response' message for each final response received from a destination, with a first line containing the message metadata (source, length, transport, address, port, time) followed by two empty tokens and the token 'continue', and with the SIP response on the following lines; once the proxy operation completes it sends a final `OK|done`.  Errors are reported with a 'NOK' status and a reason (e.g. 'Unknown transaction id: ...').

## Call detail records
If CDR generation is enabled on the server (the `cdrs` element in the configuration file) and an application has registered for one or more of the 'cdr:attempt', 'cdr:start', or 'cdr:stop' types using the 'route' command, the server sends CDR events to that application.  The first line of a CDR message contains the following tokens:

* message id
* message type ('cdr:attempt', 'cdr:start', or 'cdr:stop')
* message source ('network' or 'application')
* time of the event, in the form HH:MM:SS.uuuuuu (UTC)
* for 'cdr:start' only, the role of the server: 'uac', 'uas', 'proxy-uac', or 'proxy-uas'
* for 'cdr:stop' only, the termination reason: 'call-rejected', 'call-canceled', 'normal-release', 'session-expired', 'system-initiated-termination', or 'system-error-initiated-termination'

The associated SIP message follows on the next line.  If more than one application has registered for a CDR type, each event is delivered to only one of them (selected round-robin).  See [Call Detail Records](../srf/call-detail-records.md) for how these are surfaced in drachtio-srf.

## Outbound connections
With [outbound connections](../srf/advanced-topics.md#outbound-connections), the roles are reversed at the TCP level: the application listens for connections, and the drachtio server connects to it when an incoming request needs to be handled.  The server decides where to connect based on the [request-handlers](configuring.md#request-handlers-section) configuration -- either by querying an HTTP(S) web callback, or by connecting directly to a configured `tcp:` or `tls:` uri -- and a handler can be configured per SIP method or for all methods ('*').  The server connects using TLS if the uri specifies `transport=tls`.

Once the connection is made, the message protocol is the same as for inbound connections, with these differences:

* The application still sends the 'authenticate' message; it does so as soon as the server has connected.
* The application does not need to send 'route' commands: as soon as the server receives the 'authenticate' message on an outbound connection it delivers the incoming request that caused the connection to be made, as a 'sip' message.
* If the server is unable to connect, or to route the request over the new connection, it responds to the incoming SIP request with a 480 Temporarily Unavailable.

Finally, an HTTP web callback may instruct the server to route the request to an application that is already connected (using an inbound connection) by specifying a tag.  In that case the server selects, round-robin, a connected application that has both registered for the request type with 'route' and supplied the tag in its 'authenticate' message.
